# CLAUDE.md: Scopewise (The Estimator)

Read this at the start of every task. It condenses the kickoff spec (sections 1–9). Every rule, formula and schema below is binding.

## 1. Product

Scopewise turns a client's request into a defensible effort estimate, and gets more accurate over time. Input is a **brief pack**: emails, PDFs, meeting notes or transcripts, and/or a Jira ticket. Output:
- phases (e.g. Discovery → Design → Build → QA → Go-live) and work items;
- assumptions, missing information, likely scope additions;
- client questions ranked by how much each answer tightens the estimate;
- a range per phase and in total (P50 / P80), a visible buffer, a confidence level, and the chance of meeting the deadline.

Users change team shape (headcount per role) and watch the timeline move. Approved estimates are pushed to Jira (epic plus stories). When a project closes, actual hours from Jira feed a learning loop: an agent explains each miss, saves lessons, and an accuracy chart shows error falling over time.

Judging: depth 30%, architecture ingenuity 20%, product quality/usability 20%, complexity 15%, tech/AI 15%. A working app beats anything that doesn't run. Judges open a live URL with nothing to install.

## 2. Hard constraints

1. **Frontend runs on free GitHub Pages.** It is a static Vite build with a configurable base (`VITE_BASE`, default `/<repo-name>/`). It uses `HashRouter`. No server code, secrets or API keys go in the bundle. The repo must be public.
2. **Demo mode works with zero backend.** It covers 3 sample brief packs, scope, estimates, team what-if, the accuracy chart and the learning view. This works because:
   - the engine runs in the browser (pure TS);
   - precomputed AI outputs live in `data/demo-cache/`, generated by `scripts/precompute-demo.ts`;
   - seed history lives in `data/seed/`.
3. **The backend is a separate, portable serverless API** (`apps/api`, Hono). It handles Claude calls, Jira read/write and lessons storage. It deploys to Vercel's free tier and runs locally with `npm run dev:api`. CORS allows the Pages origin and localhost.
4. **The frontend detects the backend.** If `VITE_API_BASE_URL` is empty or `/health` fails, the app is in demo mode. Live features are then disabled with a one-line explanation: upload, live Jira sync, Push to Jira, live Ask.
5. **The LLM never produces final numbers.** Claude reads, classifies, proposes three-point guesses and explains. Every number shown is computed by the engine and is traceable to its method, inputs and formula.
6. **Reproducible.** All randomness uses the seeded PRNG (mulberry32): seed data and Monte Carlo alike.
7. **Fake data only, clearly labelled.** No real company, client or employee data.

## 3. Architecture and layout

npm workspaces monorepo, TypeScript strict everywhere.

```
apps/web        Vite + React + TS + Tailwind; Recharts; HashRouter
apps/api        Hono (Node + Vercel adapters), Anthropic SDK, Jira client, zod
packages/shared zod schemas + inferred types (web, api, engine, scripts)
packages/engine pure TS estimation engine (no I/O, no LLM), Vitest tests
prompts/        one .md per agent prompt, versioned (scope, panel-*, postmortem, ask)
data/seed       generated fake history (projects, items, worklogs, squads)
data/samples    3 sample brief packs (email.md, meeting-notes.md, jira-ticket.md each)
data/demo-cache precomputed AI outputs for the samples
scripts/        seed.ts, push-to-jira.ts, precompute-demo.ts, eval.ts
.github/workflows pages.yml (build + deploy web), ci.yml (typecheck, lint, tests)
```

Data flow: brief pack → **scope agent** → phases, items, gaps → **estimator panel** (3 agents) → three-point guesses → **engine** (similar work, bias correction, Monte Carlo, buffer, value of information) → estimate → UI. The Ask and post-mortem agents call engine functions as tools.

Storage: Jira is the system of record for history and actuals. The API keeps a small store for lessons and sync cache: Supabase Postgres if `DATABASE_URL` is set, otherwise a JSON file. In demo mode the frontend keeps new lessons in `localStorage`, with every access in try/catch.

Model: Anthropic SDK, model from `ANTHROPIC_MODEL` (default: current Sonnet). Use tool use / structured output validated with zod. On a validation failure, retry once with the error, then fail gracefully.

## 4. Domain schemas (packages/shared)

- `BriefPack { id, title, clientDeadline?, sources: { kind: 'email'|'pdf'|'notes'|'transcript'|'jira', name, text }[] }`
- `ProjectType = 'new-feature'|'form-digitization'|'integration'|'data-migration'|'reporting'`; `Size = 'S'|'M'|'L'|'XL'`
- `Phase { id, name, order, role }`. Templates:
  - new-feature: Discovery → Design → Build → QA → Go-live
  - form-digitization: Form analysis → Legal review → Build form → Integration → QA → Go-live
  - integration: Discovery → API mapping → Build → Integration testing → Go-live
- `WorkItem { id, phaseId, title, category, complexity: 'S'|'M'|'L', role, o, m, p, sourceRefs[], affectedByQuestions[] }` (hours)
- `MissingInfo { id, question, why, affectedItemIds[], spreadMultiplier }`
- `ScopeRisk { id, description, likelihood, evidenceProjectIds[], addedHoursRange }`
- `ScopeResult { projectType, size, phases, items, assumptions[], outOfScope[], missingInfo[], scopeRisks[], clientEmailDraft }`
- `PanelResult { agents: { persona, items: { itemId, o, m, p, reason }[] }[], rounds: 2, disagreementFlags[] }`
- `TeamShape { [role]: headcount }`; `SquadStats { focusFactor, absenceRate, coordinationOverheadPerExtra }`
- `Estimate { perPhase[], total: { p50, p80 }, buffer: { task, missingInfo, availability, total }, commitDate, onTimeProbability, confidence: 'High'|'Medium'|'Low', rankedQuestions[], analogs[], explanations: Record<numberId, Explanation> }`
- `Explanation { method, citation, plainWords, formula?, inputs: Record<string, number|string> }`
- `HistoryProject`, `HistoryItem` (`originalEstimateH`, `timeSpentH`, labels), `Worklog`, `Lesson { projectId, cause: 'scope-added'|'underestimated'|'blocked'|'availability'|'data-error', note, appliesTo: { category?, projectType? } }`

## 5. Engine (packages/engine): exact methods

Every exported function also returns an `Explanation`, which the UI shows in a "How was this calculated?" drawer. Tests come first.

1. **Reference class** (Kahneman & Tversky 1979; Flyvbjerg 2006). Input: projectType + size. Output: the distribution of actual total hours for matching closed projects (median, P20, P80, n). UI copy: "projects like this took X–Y hours".
2. **Analogies** (Shepperd & Schofield 1997). For each item, find the k=3 most similar closed items: same category first, then complexity, then TF-IDF cosine on text. Return their actual hours.
3. **Panel aggregation** (Wideband Delphi; Boehm 1981). Three personas (delivery lead, QA lead, domain expert) give o/m/p with reasons, then revise in round 2. Aggregate o = min, m = median, p = max. Flag an item if the coefficient of variation of m > 0.35.
4. **Blend:** m' = w·median(analog actuals) + (1−w)·m_panel, where w = n/(n+3).
5. **Bias correction** (Spolsky 2007 EBS; Efron & Morris 1975 shrinkage). Per category: log r_c = (n_c/(n_c+k))·mean(log(actual/estimate)), k = 5. Multiply each item's o/m/p by r_c.
6. **PERT sampling** (Malcolm et al. 1959): Beta-PERT(o, m', p).
7. **Monte Carlo** (Metropolis & Ulam 1949): 5,000 runs (1,000 for live what-if), mulberry32. Each run:
   - samples every item;
   - converts role hours to calendar time using team shape, focus factor and Brooks overhead (each extra person in a role adds 10% to that role's hours; a constant calibrated from history);
   - removes random capacity at the absence rate;
   - runs phases in order, with a phase's items in parallel across its role's headcount.
   Outputs: P50/P80 hours per phase and total, the finish-date distribution, and P(finish ≤ deadline).
8. **Buffer** (Goldratt 1997; Newbold 1998 root-square):
   - task: B_task = √Σ(P80_i − P50_i)²;
   - missing info: the extra spread of each open question's affected items (via `spreadMultiplier`);
   - availability: absenceRate × standard hours.
   Commit = ΣP50 + buffer. The buffer is drawn as its own bar.
9. **Confidence:**
   - High if P80/P50 < 1.25 and there are no high-impact open questions;
   - Low if P80/P50 > 1.6 or there are 3+ open questions;
   - otherwise Medium.
10. **Value of information** (Howard 1966). Re-simulate with each question's affected spread removed, then rank questions by the reduction in (P80 − P50). UI copy: "Ask this first: it narrows the range by ~X hours."
11. **Accuracy** (Conte, Dunsmore & Shen 1986): MMRE, PRED(25), P80 hit rate.
12. **Backtest:** replay closed projects in date order, estimating each from earlier projects only. Report per-project error, raw panel vs calibrated. Chart: x = project order, y = rolling MMRE, two lines.
13. **Team what-if:** a pure `(estimateInputs, teamShape) → estimate`, fast enough for a debounced slider.

## 6. AI layer (apps/api + prompts/)

- **Scope agent:** brief pack → `ScopeResult`. Cites a `sourceRefs` source for every item, never invents client facts, and puts unknowns in `missingInfo`. Its context includes the phase template for the detected type and the top lessons for that type.
- **Estimator panel:** 3 persona prompts, 2 rounds, run in parallel → `PanelResult`. Each persona sees the analogs' actual hours.
- **Scope-risk predictor:** the engine finds items commonly added after kickoff in similar past projects; Claude phrases them as client questions.
- **Post-mortem agent:** compares estimate vs actual per phase and item, classifies each miss as a `Lesson.cause`, writes a one-line lesson, and flags suspected data-entry errors (e.g. time spent 10× the estimate).
- **Ask agent:** tools `get_estimate`, `explain_number`, `run_what_if(teamShape | dropItemIds)`, `answer_question(questionId, answer)`. The tools call the engine; the agent only phrases results.
- **Wording rule (every prompt):** talk about work, skills and capacity. Never mention individuals' performance or personal circumstances.
- **Endpoints:** `GET /health`, `POST /scope`, `POST /panel`, `POST /estimate`, `POST /ask`, `POST /postmortem`, `GET /jira/history`, `POST /jira/push`, `GET/POST /lessons`. Rate-limit and size-limit uploads. PDFs are parsed server-side or sent to Claude as documents.

## 7. Jira (real, with fake data)

- Jira Cloud REST v3, basic auth (`JIRA_EMAIL` + `JIRA_API_TOKEN`), `JIRA_BASE_URL`, `JIRA_PROJECT_KEY`. Credentials stay in the API.
- Labels: `type:form-digitization`, `size:M`, `phase:design`, `cat:integration`, `squad:alpha`, `client:<fake>`.
- **Read:** epics = projects, child issues = items, with `timeoriginalestimate`, `timespent`, labels, created/resolution dates. Worklogs are summed per squad per week to give focus factor and absence rate. Cache in the store; refresh on demand.
- **Push:** an epic plus one story per item, with original estimate = P50, phase/category labels, and a description linking back to the estimate. Read issue-type metadata to link stories to the epic (`parent`) instead of assuming.
- `scripts/push-to-jira.ts` loads `data/seed` idempotently, keyed by a seed-ID label.
- CSV timesheet import (`date, squad, role, hours`) is the fallback source for worklogs.

## 8. Seed, UI, milestones

**Seed** (`scripts/seed.ts`, fixed seed): 3 squads × 4–8 people (roles only), 40 closed projects over 18 months (~400 items), plus the 3 open samples. Planted patterns:
- integrations overrun ~1.4×; reporting comes in ~0.9×;
- form digitizations often add an e-signature step after kickoff;
- ~8% absence, plus one planned leave inside an open project's window;
- the first 10 projects are noisier, so the backtest visibly improves.

**Samples** (email + meeting notes + Jira ticket each, with deliberate gaps):
1. new-feature: automated reminders for investors who haven't signed;
2. form-digitization: paper subscription form online, connected to records;
3. integration: sync investor data with a fund administrator's system.

**Screens:**
1. Home/Intake: start card, 3 sample cards, mode indicator, upload, deadline, team shape.
2. Scope: phases + items with source chips, assumptions, missing info, scope risks, client email with ranked questions (copy).
3. Estimate: headline range + commit date, on-time chance, confidence badge, per-phase range bars with a separate buffer segment, Gantt timeline, analogs, and "answer a question" (tightens live). A "How was this calculated?" drawer on every number.
4. Team & timeline: headcount steppers, live finish/hours/on-time chance, Push to Jira.
5. Learning: closed projects (estimate vs actual), why-we-missed notes, lessons, accuracy chart (raw vs calibrated rolling MMRE), P80 hit rate.
6. Ask: a chat side panel on every screen (scripted in demo mode).
7. About: SVG architecture diagram, methods table with citations, data disclaimer, Manager/Overseer view explanation.

One line of helper text under each key number; no tours. Keyboard navigable, sufficient contrast, readable at mobile width.

**Milestones:** M0 setup → M1 seed → M2 scope agent → M3 engine → M4 estimate screen + demo mode (Day 1 gate) → M5 what-if + VOI → M6 Jira both ways → M7 learning loop → M8 Ask + scope-risk → M9 polish.
**Cut order if behind:** Ask → scope-risk → Push to Jira → post-mortem agent. **Never cut:** the estimate path, demo mode on Pages, reading Jira history, the accuracy chart.

## 9. Working rules

- TypeScript strict; zod at every boundary; no `any` in engine or shared.
- The engine is pure and fully tested; no LLM or I/O inside it.
- Prompts live in `prompts/`. Store `promptVersion` with every AI output. `npm run eval` checks the samples: item count, phase coverage, and whether the questions mention the planted gaps.
- Never commit secrets. `.env` is git-ignored; `.env.example` documents every variable.
- Small commits with clear messages.
- README covers: problem, live URL, architecture, methods + citations, run locally, deploy (Pages + API), what is fake.
- If a decision isn't covered here, pick the simplest option that keeps demo mode working on Pages, record it under **Decisions**, and continue.

## Design system ("dithered printout")

The user asked for an ASCII-art and dithering theme. The concept: **the estimate is a printout from an estimating machine, and dither density encodes certainty.**

- **Palette (light, "ledger paper"):** paper `#E8EAE3`, ink `#1A1F3A`, riso blue `#2F43D8`, fluoro pink `#E8366A` (buffer, risk, deadline), graphite `#5D6177`.
- **Palette (dark, "screen"):** `#0F1226` bg, `#E3E6F0` ink, `#8C99FF` blue, `#FF6F93` pink, `#9AA0B8` graphite.
- **Type:** Martian Mono for display, numbers and ASCII art; Atkinson Hyperlegible Next for body text.
- **Signature element:** ordered (Bayer 4×4) dither in range bars and distributions.
  - P50 core: solid ink.
  - P50→P80: 50% dither.
  - Tail: 12.5% dither.
  - Buffer: pink dither.
  The hero is a Monte Carlo histogram filling in with dithered ink. It is the only autonomous motion.
- **ASCII:** pure 7-bit ASCII only (`+ - | = # . :`), so glyph coverage is never an issue. Boxes have `+` corners, rules are drawn with `-`, and buttons read `[ Run estimate ]`.
- **Rules:**
  - sentence case everywhere and no all-caps eyebrows;
  - no gradients and no drop shadows: depth comes from dither and offset ink only;
  - square corners;
  - `prefers-reduced-motion` disables the histogram animation.

## Decisions

- **No Anthropic key in the build session:** the files in `data/demo-cache/` were not produced by Claude.
  - Scope results are hand-written fixtures (`promptVersion: "fixture-…"`).
  - Panel outputs and post-mortem notes come from deterministic offline heuristics in `packages/engine/src/offline.ts` (`promptVersion: "offline-heuristic-…"`).
  - `npm run precompute` regenerates everything with real Claude calls once `ANTHROPIC_API_KEY` is set.
  - The UI labels where each output came from.
- **Calendar model:** 6 productive hours per person-day × focus factor; 5-day weeks; no holidays except the planned leave in squad data.
- **Bundler:** Vite 7. **zod:** v4.
- **Demo data in the bundle:** `apps/web` imports `data/seed` and `data/demo-cache` as JSON via a Vite alias (`@data`), so the Pages build is self-contained.
- **Role set:** `pm`, `designer`, `engineer`, `qa`, `legal`. Each phase has one role.
