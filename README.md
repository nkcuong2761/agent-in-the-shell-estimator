# Scopewise: estimates that learn

**The problem.** A client sends a few emails, a meeting transcript and a Jira ticket, and someone has to say how long it will take. The answer is usually one number. It has no visible assumptions and no record of how wrong the last one was.

**Scopewise** turns that brief pack into an effort estimate you can defend:
- It splits the work into **phases and work items**, each citing the source line it came from.
- It lists **assumptions, missing information and likely scope additions**.
- It ranks client questions by **how much each answer would narrow the estimate**.
- It gives a **P50 to P80 range** per phase and in total, with **one visible buffer**, a **confidence level** and the **chance of meeting the deadline**.

Change the team shape and the timeline moves. Push the approved estimate to Jira as an epic with stories. When projects close, actual hours feed back in: a post-mortem explains each miss, lessons are saved, and the accuracy chart shows error falling.

**Live demo:** `https://<user>.github.io/agent-in-the-shell-estimator/`. It runs entirely in the browser with no backend; [SETUP.md](SETUP.md) explains how to publish it.

> **Everything is fictional.** Clients, people, squads, projects and hours are invented and generated by a seeded script.

## What to try (no install)

Each estimate is a document; a small assistant in the corner answers edge cases and updates the page when asked.

1. **Home** lists every estimate and finished project in one table, with three tiles above it. Open a row.
2. The **estimate card** shows the pure effort in working hours, the working time in weeks for your team, and how sure the estimate is, with "Why this estimate and confidence?" one click away.
3. Change the **team structure** (half a developer counts), the **working hours** (days a week × hours a day) or the **schedule** (start and due dates). The numbers update in place; the page never jumps.
4. The **realistic forecast** adds what is known to cost time in this window: the team's planned leave, delays seen on similar projects, and your own risks and buffer. Untick any of them. A tag says whether it meets the due date.
5. Open a stage under **What happens when** to see its work items, each linked to the source it came from. **Ask the client before you commit** lists the three questions that tighten the estimate most.
6. Press **✦ Ask Scopewise** for follow-ups in plain words. They run on the real engine in your browser, even in demo mode:
   - "What if we add another developer?" shows a comparison. **Use this** makes it the current estimate.
   - "Can we finish by 11 Dec?" · "Why does build take so long?" · "What if we skip QA?" · "The client says email only, no SMS"
7. Finished projects (from Home) show what we said against what it took, what happened, the lesson learned, and whether estimates are getting better.
8. **See the full working and methods** and **Help** show every formula, input and citation. Technical terms appear only there.

## Architecture

```
 brief pack ──> scope agent ──> estimator panel ──> ENGINE ──> estimate ──> push to Jira
 (email, notes,  (Claude:        (Claude: 3 personas   (pure TS,   (P50/P80,
  PDF, Jira)      phases, items,  x 2 rounds, o/m/p)    seeded,     commit date,
                  cited sources,                         in the      on-time %)
                  open questions)                        browser)
                       ^                                   ^              ^
                       | top lessons per type              | history      | Ask agent (tools call the engine)
 Jira Cloud ──> history ──> post-mortem agent ──> lessons store
```

| Part | What it is |
|---|---|
| `apps/web` | Vite + React + TypeScript + Tailwind, HashRouter, static build for GitHub Pages. The engine runs in the browser. `present/` turns its output into plain language, and `copy.ts` holds every phrase. Conversations are stored in localStorage. Demo data is bundled from `data/`. |
| `apps/api` | Hono API (Node + Vercel adapters). It holds the secrets and handles Claude calls, Jira read/write and the lessons store (Postgres or a JSON file). |
| `packages/engine` | The estimation engine: pure TypeScript with no I/O and no LLM. Every function returns its result plus an `Explanation`. 31 Vitest tests. |
| `packages/shared` | zod schemas and types used at every boundary. |
| `prompts/` | One versioned prompt per agent. Every AI output stores its `promptVersion`. |
| `data/` | `seed/` (fake history), `samples/` (3 brief packs), `demo-cache/` (precomputed AI outputs). |
| `scripts/` | `seed.ts`, `precompute-demo.ts`, `push-to-jira.ts`, `eval.ts`. |

**Demo mode vs live mode.** The site calls `GET /health` on `VITE_API_BASE_URL`. With no API, or an API that doesn't respond, the full demo still works: the engine, bundled history, precomputed agent outputs and a rule-based follow-up parser. A pasted brief is read in the browser by the engine's rule-based reader (see below). Live-only features say why they're off:
- uploaded files and Jira tickets (the API reads them);
- open-ended questions answered by the Ask agent.

**No Claude key?** The API still estimates. `POST /scope` and `POST /panel` use the engine's rule-based reader and fixed-lens panel (`packages/engine/src/offlineScope.ts`, `offline.ts`) when `ANTHROPIC_API_KEY` is unset, and also when Claude fails (no credit, bad key, outage). The response carries a `note` saying so, the brief card says "prepared offline", and every number still comes from the engine: analogs, bias correction and the simulation are unchanged. The reader picks the phase template whose keywords the brief mentions most, adds work items for features it names (e-signature, reminders, PDFs, exports, bank details, uploads, …) with the sentence that triggered each as its citation, and asks that template's usual open questions. Claude reads briefs better; the rules keep the product usable for free.

In live mode, conversations are also saved to the API store.

## Methods

| Step | Method | Citation |
|---|---|---|
| Outside view | Reference class: P20/median/P80 of actual hours for the same type and size | Kahneman & Tversky (1979); Flyvbjerg (2006) |
| Similar work | k = 3 nearest past items: same category, then complexity, then TF-IDF cosine | Shepperd & Schofield (1997) |
| Panel | Wideband Delphi, 3 personas × 2 rounds: o = min, m = median, p = max; flag if CV(m) > 0.35 | Boehm (1981) |
| Blend | m′ = w·median(analogs) + (1−w)·r_c·m_panel, w = n/(n+3) | Shepperd & Schofield (1997) |
| Bias | log r_c = n_c/(n_c+5) · mean log(actual/estimate), with coordination overhead divided out | Spolsky (2007); Efron & Morris (1975) |
| Items | Beta-PERT(o, m′, p) | Malcolm et al. (1959) |
| Simulation | 5,000 seeded runs (mulberry32): one shared project error factor, a shared factor per open question, Brooks overhead (+10% per extra person), absence, planned leave; phases in order, items in parallel across headcount | Metropolis & Ulam (1949); Brooks (1975) |
| Buffer | √Σ(P80ᵢ − P50ᵢ)² + open-question spread + absence × ΣP50; commit = ΣP50 + buffer | Goldratt (1997); Newbold (1998) |
| Confidence | High if P80/P50 < 1.25 and no high-impact questions are open; Low if P80/P50 > 1.6 or 3+ questions are open | — |
| Questions | Value of information: re-simulate with each question answered (common random numbers) and rank by the drop in P80 − P50 | Howard (1966) |
| Accuracy | MMRE, PRED(25), P80 hit rate; walk-forward backtest using only earlier projects | Conte, Dunsmore & Shen (1986) |

Two modelling choices go beyond the brief. Both are documented in the drawers and in `CLAUDE.md` under Decisions:
- **Items run late together.** Without a shared project-level factor, independent items average out and P80 sits only ~4% above P50. With it, the backtest's P80 hit rate is ~78%.
- **An open question is one unknown.** It moves all its items together, which makes value of information meaningful: answering the SMS question narrows the reminders estimate by ~17h.

Backtest on the seed history: the raw panel is off by **19%** on average, the calibrated engine by **15%**. Within-25% accuracy rises from 68% to 83%, and the first five projects are ~24% off against ~14% for the last five.

## Run locally

```bash
npm install
npm run dev          # web, demo mode: http://localhost:5173
npm run dev:api      # API: http://localhost:8787 (copy apps/api/.env.example to apps/api/.env first)
VITE_API_BASE_URL=http://localhost:8787 npm run dev   # web in live mode
```

Checks (all run in CI):

```bash
npm run typecheck && npm run lint && npm test && npm run eval && npm run build
# npm test runs the engine tests (35, incl. the rule-based reader), the web tests and the API tests (Jira import mapping and routes)
```

Data:

```bash
npm run seed                       # regenerate data/seed (fixed seed 1789)
npm run precompute                 # regenerate data/demo-cache offline
npm run precompute -- --live       # ...with real Claude (needs ANTHROPIC_API_KEY)
npm run push-to-jira -- --dry-run  # load the seed history into Jira Cloud (idempotent)
```

## Deploy

- **Web → GitHub Pages:** `.github/workflows/pages.yml` builds on every push to `main`. Set Pages → Source to GitHub Actions, and make the repo public.
- **API → Vercel:** set the root directory to `apps/api` and add the env vars from `apps/api/.env.example`. Then set the repo variable `VITE_API_BASE_URL` to the API URL.

Exact clicks are in [SETUP.md](SETUP.md).

## What's fake, and where AI outputs come from

- **Seed history:** generated by `scripts/seed.ts` with planted patterns:
  - integrations overrun ~1.4×, reporting comes in at ~0.9×;
  - form digitizations often add e-signature after kickoff;
  - ~8% absence, plus one planned leave;
  - the first 10 projects are noisier;
  - two time-entry typos.
- **Real tickets you import** (Attach Jira → a finished ticket) are the one exception: they come from your own Jira, carry the label `real`, show "Real ticket" on their page and "· real" in the table, and are added to the seed history for analogs, bias correction and the accuracy chart.
- **Sample brief packs:** written for this project, with deliberate gaps (`data/samples/*/brief.json` lists them).
- **Demo cache:** no API key was available when this repo was built, so the committed cache is labelled honestly. The UI shows each output's provenance:
  - scope results are hand-written fixtures that follow the scope prompt's contract (`fixture-scope@1`);
  - panel guesses and post-mortem notes come from deterministic offline heuristics (`offline-heuristic-*`);
  - briefs you paste without a Claude key are read by the rule-based reader (`offline-heuristic-scope@1`).
  
  Run `npm run precompute -- --live` with a key to replace them with Claude output. `npm run eval` checks either version.
